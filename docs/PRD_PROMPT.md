# PRD 생성 메타 프롬프트: 노션 기반 견적서 웹 뷰어 MVP

> 이 문서는 `prd-generator` 에이전트가 PRD를 작성할 때 사용하는 지침 프롬프트입니다.
> 아래의 지침을 그대로 AI에게 전달하면 완성도 높은 PRD를 생성할 수 있습니다.

---

## 에이전트 지침 (prd-generator)

당신은 SaaS MVP PRD 전문 작성 에이전트입니다.
아래 컨텍스트와 요구사항을 바탕으로 완전한 PRD 문서를 한국어 마크다운 형식으로 작성하세요.

### 작성 원칙

1. 모든 기능에는 고유 ID를 부여하고 (F001, F002... 형식), 페이지/메뉴와 교차 참조할 것
2. 기능 명세 → 메뉴 구조 → 페이지 상세 간의 정합성을 반드시 검증할 것
3. Notion API 연동 섹션은 별도로 분리하여 기술적 제약과 데이터 흐름을 명확히 기술할 것
4. MVP 범위를 엄격히 지키고, MVP 이후 기능은 별도 항목으로 분리할 것
5. 데이터 모델은 필드명, 타입, 관계를 모두 명시할 것
6. 문서 마지막에 정합성 검증 체크리스트를 포함할 것

---

## 프로젝트 컨텍스트

### 서비스 개요

- **서비스명**: 노션 기반 견적서 웹 뷰어 (invoice-web)
- **목적**: 프리랜서/에이전시가 노션(Notion)에서 작성한 견적서를 클라이언트가 웹 브라우저로 확인하고 PDF로 다운로드할 수 있는 공유 링크 서비스
- **핵심 가치 제안**: 별도 견적서 소프트웨어 없이 기존에 사용하던 노션 페이지 URL만으로 전문적인 견적서 공유 링크를 즉시 생성
- **타겟 사용자**:
  - **프리랜서/에이전시** (서비스 주 사용자): 노션에서 견적서를 작성하고, 클라이언트에게 공유 링크를 발송하는 주체
  - **클라이언트** (견적서 수신자): 별도 계정 없이 공유 링크만으로 견적서를 확인하고 응답하는 주체

## Notion API 연동 상세 지침

### 1. 연동 방식

이 서비스에서 노션은 **영구 데이터베이스가 아닌 1회성 입력 소스**로 사용됩니다.

```
데이터 흐름:
노션 페이지 URL 입력
  → 서버에서 Notion API 호출 (pages.retrieve + blocks.children.list)
  → 응답 파싱 (페이지 메타 + 테이블 블록)
  → Supabase에 구조화된 데이터로 저장
  → 이후에는 Supabase 데이터만 사용 (노션 재호출 없음)
```

### 2. Notion API 인증 방식

- **방식**: Internal Integration Token (서버 환경변수 방식)
- **환경변수**: `NOTION_API_TOKEN` (절대 `NEXT_PUBLIC_` 접두사 사용 금지)
- **온보딩 마찰 포인트**: 프리랜서가 자신의 노션 페이지를 Integration에 연결해야 함 (페이지 우측 상단 → 연결 → Integration 추가)
- **MVP 전략**: 서비스 전용 Integration 1개를 운영자가 생성하고 사용자에게 페이지 공유 방법을 안내하는 방식으로 온보딩 마찰 최소화

### 3. 페이지 ID 추출 방식

노션 URL에서 페이지 ID를 추출할 때 반드시 UUID 형식으로 변환해야 합니다.

```
입력 URL 예시:
https://www.notion.so/My-Invoice-abc123def456789012345678901234ab

추출 로직:
1. URL 마지막 세그먼트에서 32자리 hex 문자열 추출
2. 8-4-4-4-12 패턴으로 UUID 변환
   abc123de-f456-7890-1234-5678901234ab
```

### 4. 견적서 데이터 파싱 전략

노션 견적서 페이지는 다음 구조를 가정합니다.

```
견적서 페이지 구조 (노션):
├── Properties (페이지 메타데이터)
│   ├── title: 견적서 제목
│   ├── rich_text: 발행인 정보, 날짜 등
│   └── number: 합계 금액 (선택)
└── Body (블록)
    └── table 블록 (첫 번째 테이블이 견적 항목)
        ├── 헤더 행: [항목명, 설명, 수량, 단가, 금액]
        └── 데이터 행: 각 견적 항목
```

**테이블 블록 파싱 시 3단계 API 호출 필요**:

```
1단계: pages.retrieve(pageId)
  → 페이지 Properties 획득

2단계: blocks.children.list(pageId)
  → 페이지 본문 블록 목록 획득 (table 블록 ID 확인)

3단계: blocks.children.list(tableBlockId)
  → table_row 블록 목록 획득 (실제 셀 데이터)
```

### 5. Rate Limit 처리

- Notion API 제한: **3 req/s**
- 재시도 전략: `exponential backoff` (2^attempt 초, 최대 3회)
- 429 에러 수신 시 `Retry-After` 헤더 값 우선 적용

### 6. Notion API 관련 코드 위치 규칙

- 모든 Notion API 코드는 `src/lib/notion/` 디렉토리에 위치
- Server Actions에서만 호출 (클라이언트 컴포넌트에서 직접 호출 금지)
- API 토큰이 클라이언트 번들에 포함되지 않도록 반드시 서버 전용 처리

## PRD 작성 요구사항

아래 7개 섹션을 모두 포함하는 완성된 PRD를 작성하세요.

### 섹션 1: 핵심 정보

다음 항목을 포함하세요.

- 서비스 목적 (1~2문장 핵심 요약)
- 타겟 사용자 (프리랜서/에이전시, 클라이언트 각각의 역할과 니즈)
- 핵심 가치 제안
- MVP 성공 지표 (3~5개)

### 섹션 2: 사용자 여정

두 개의 플로우를 텍스트 다이어그램(아스키 아트)으로 표현하세요.

**플로우 A - 프리랜서 여정**:
로그인 → 대시보드 → 견적서 작성(노션 URL 입력) → 임포트 완료 → 클라이언트 정보 입력 → 발송 → 링크 생성 완료

**플로우 B - 클라이언트 여정**:
공유 링크 클릭 → 토큰 검증 → 견적서 웹 뷰 확인 → (PDF 다운로드 | 승인/거절) → 응답 완료

### 섹션 3: 기능 명세

다음 형식의 테이블로 작성하세요.

```
| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
```

MVP 핵심 기능 (F001~F006):
- F001: 노션 API 연동 (노션 URL 파싱 및 데이터 임포트)
- F002: 견적서 발송 및 공유 링크 생성 (고유 토큰 기반)
- F003: 견적서 웹 뷰 (클라이언트 공개 링크 접근)
- F004: PDF 다운로드 (견적서 PDF 변환 및 다운로드)
- F005: 견적서 상태 관리 (승인/거절/보류 상태 추적)
- F006: 견적서 목록 조회 (프리랜서 대시보드)

MVP 필수 지원 기능 (F010~F012):
- F010: 기본 인증 (회원가입/로그인/로그아웃, Supabase Auth)
- F011: 프리랜서 기본 정보 (이름, 이메일, 회사명)
- F012: 클라이언트 기본 정보 (이름, 이메일, 회사명)

MVP 이후 기능 (별도 섹션으로 목록화):
결제/인보이싱, 전자서명, 클라이언트 계정 기반 협상, 노션 자동 동기화, 다국어, 실시간 알림

### 섹션 4: 메뉴 구조

아스키 아트 트리 형식으로 작성하되, 각 메뉴 항목에 구현 기능 ID를 명시하세요.

```
비로그인 사용자 메뉴 (로그인, 회원가입)
로그인 사용자 메뉴 (대시보드, 새 견적서 작성, 계정)
클라이언트 공개 링크 (견적서 뷰)
```

### 섹션 5: 페이지별 상세 기능

아래 8개 페이지 각각에 대해 다음 형식의 테이블로 작성하세요.

```
| 항목 | 내용 |
- 역할
- 진입 경로
- 사용자 행동
- 주요 기능 (불릿 리스트)
- 다음 이동 (성공/실패 케이스)
```

작성 대상 페이지:
1. 로그인 페이지 (F010)
2. 회원가입 페이지 (F010, F011)
3. 대시보드 - 견적서 목록 (F006)
4. 견적서 작성 페이지 - 노션 URL 입력 (F001)
5. 견적서 상세 페이지 - 발송 준비 (F002, F005, F011, F012)
6. 발송 완료 페이지 (F002)
7. 견적서 뷰 페이지 - 클라이언트 (F003, F004, F005)
8. 견적서 응답 완료 페이지 (F005)

### 섹션 6: 데이터 모델

Notion 연동 필드를 포함하여 4개 테이블의 스키마를 작성하세요.

각 테이블에 `| 필드 | 설명 | 타입 |` 형식의 테이블을 사용하세요.

**Freelancer 테이블**: id, email, name, company_name, password_hash, created_at, updated_at

**Invoice 테이블** (Notion 연동 핵심):
- id, freelancer_id (FK), notion_url (원본 노션 URL 보존), client_name, client_email, client_company
- status (enum: draft | sent | approved | rejected)
- share_token (고유 공유 링크 토큰, UUID 기반)
- total_amount, created_at, updated_at, expires_at (공유 링크 만료 30일)

**InvoiceItem 테이블** (노션 테이블 블록 파싱 결과):
- id, invoice_id (FK), title, description, quantity, unit_price, amount (파생값), order (정렬 순서)

**InvoiceResponse 테이블** (클라이언트 응답):
- id, invoice_id (FK), status (enum: approved | rejected | pending), notes (거절 사유), responded_at

### 섹션 7: 기술 스택

다음 카테고리별로 기술 스택과 버전을 작성하세요.

- 프론트엔드 프레임워크: Next.js 15.5.3 (App Router + Turbopack), TypeScript 5, React 19.1.0
- 스타일링 & UI: TailwindCSS v4, shadcn/ui (new-york), Lucide React, Radix UI
- 폼 & 검증: React Hook Form 7.x, Zod
- 백엔드 & DB: Supabase (Auth + PostgreSQL), Server Actions (Next.js)
- Notion 연동: @notionhq/client (공식 SDK), Internal Integration Token
- PDF 생성: html2pdf 또는 jsPDF + html2canvas (클라이언트 사이드 렌더링 기반)
- 이메일: Resend 또는 Nodemailer (트랜잭션 이메일)
- 배포: Vercel

## 정합성 검증 지침

PRD 작성 완료 후 반드시 아래 4단계 체크리스트를 수행하고 결과를 문서에 포함하세요.

**1단계: 기능 명세 → 페이지 연결 검증**
- 기능 명세의 모든 기능 ID (F001~F012)가 페이지별 상세 기능에 존재하는지 확인
- 기능 명세의 "관련 페이지" 항목이 실제 페이지 이름과 일치하는지 확인

**2단계: 메뉴 구조 → 페이지 연결 검증**
- 메뉴 구조의 모든 항목이 페이지별 상세 기능에 대응하는지 확인
- 메뉴에서 참조하는 기능 ID가 기능 명세에 정의되어 있는지 확인

**3단계: 페이지별 상세 기능 → 역참조 검증**
- 페이지에 명시된 모든 구현 기능 ID가 기능 명세에 정의되어 있는지 확인
- 모든 페이지가 메뉴 구조 또는 사용자 여정을 통해 접근 가능한지 확인

**4단계: 누락 및 고아 항목 검증**
- 기능 명세에만 있고 페이지에서 구현되지 않은 기능 확인
- 페이지에만 있고 기능 명세에 없는 기능 확인
- 메뉴에만 있고 실제 페이지가 없는 항목 확인

## 출력 형식 지침

- 전체 문서를 한국어로 작성
- 마크다운 형식 사용 (헤더, 테이블, 코드 블록, 불릿 리스트)
- 이모지를 섹션 헤더에 활용하여 가독성 향상
- 페이지별 섹션은 `---` 구분선으로 분리
- 데이터 타입은 영어로 표기 (String, UUID, Timestamp, Decimal, Integer, Enum)
- 코드 예시나 API 흐름은 코드 블록으로 표현

## 참고: 이 프로젝트의 기술적 제약 사항

PRD 작성 시 아래 제약 사항을 기능 명세와 페이지 상세에 반영하세요.

| 제약 사항 | 내용 | PRD 반영 방법 |
|----------|------|-------------|
| Notion API Rate Limit | 3 req/s | 임포트 기능에 로딩 상태 및 에러 처리 명시 |
| 테이블 블록 파싱 복잡도 | 3단계 API 호출 필요 | 견적서 작성 페이지에 로딩 UX 요구사항 포함 |
| Integration 온보딩 마찰 | 노션 페이지에 Integration 연결 필요 | 견적서 작성 페이지에 가이드 UI 요구사항 포함 |
| URL → UUID 변환 | 32자리 hex를 UUID로 변환 | 견적서 작성 페이지 URL 유효성 검사 요구사항에 포함 |
| 공유 링크 만료 | 30일 후 만료 | 견적서 뷰 페이지 토큰 만료 에러 처리 명시 |
| 클라이언트 비인증 접근 | share_token만으로 접근 | 견적서 뷰 페이지 보안 요구사항에 포함 |
